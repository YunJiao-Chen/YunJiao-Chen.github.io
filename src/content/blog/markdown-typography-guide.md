## 为什么中文排版值得单独写一条规范

英文排版的默认值几乎是为中文反向优化的。西文的字面窄、词之间有空格，所以 16px 字号配 1.5 倍行高看起来还算舒服；中文方块字的字面几乎占满字身，同样的参数会让整段文字显得**拥挤且沉重**。我做博客改版时做了一次实测：同一篇文章在 16px/1.5 和 17px/1.75 两组参数下，前者平均阅读完成率低了大约 10 个百分点。样本不大，但方向足够明确。

排版不是审美问题，是**阅读耐力**问题。读者在手机上读一篇 3000 字的技术文章，眼睛和注意力都在持续消耗，排版的职责是把这份消耗降到最低。

## 字号、行高与段间距

我最后定下来的规范如下。它没什么独创性，但每一项都能说出理由：

| 元素 | 取值 | 理由 |
| --- | --- | --- |
| 正文字号 | 17px | 中文笔画密度高，16px 在移动端偏小 |
| 正文行高 | 1.75 | 中文行间需要更多空气，1.5 会显得粘连 |
| 段间距 | 1.5em | 与行高形成约 2 倍的关系，段落边界一眼可辨 |
| 内容最大宽度 | 40em | 超过约 45 个汉字/行，回扫就变得困难 |
| 代码字号 | 15px | 等宽字体视觉偏大，等比缩小一档更协调 |

这些值全部用 CSS 变量集中管理，这样导出到公众号时只需替换变量，而不是逐条改样式：

```css
:root {
  --font-size-body: 17px;
  --line-height-body: 1.75;
  --paragraph-gap: 1.5em;
  --measure: 40em;
  --code-font: "JetBrains Mono", "SFMono-Regular", Consolas, monospace;
}

.prose p {
  margin: 0 0 var(--paragraph-gap);
  font-size: var(--font-size-body);
  line-height: var(--line-height-body);
  max-width: var(--measure);
  text-wrap: pretty;
}
```

`text-wrap: pretty` 能让最后一行尽量不出现孤零零的两三个字，代价几乎为零，值得加。

## 中英混排的空格

这是中文排版里争议最大的一条，我的态度是：**在中文与拉丁字母、数字之间加一个可感知的间隙，但不直接写空格字符**。直接敲空格的坏处是复制到别处会带出多余空白，也让同一段文字在不同工具里宽度不一致。

实现方式有两种：

1. 用 `text-autospace` 之类的浏览器能力（支持度还在推进，适合渐进增强）。
2. 在渲染层给「中文 + 拉丁」的边界插入 `<span class="spacer">`，需要时用 `display: inline-block; width: 0.25em` 控制。

无论用哪种，都要遵守几个例外：标点前后不加空格；全角标点（，。！？）与英文之间不加；代码与链接内部一律不动。这类「大部分加、少数不加」的规则，是自动处理最容易做错的部分，所以我把例外清单写进了构建期的检查脚本里。

## 代码块与图片说明

技术博客的代码块承担了大量信息量，值得单独对待：

- 代码块必须有**等宽字体回退链**，最后一定要落到 `monospace`，否则中文字体可能接手渲染。
- 横向滚动要显式开启（`overflow-x: auto`），但**不要**用 `word-break` 拆断长行，那会让代码失去可直接复制的价值。
- 代码块上下留白要大于段间距，才能把它和正文段落区隔开。
- 图片下方必须有说明文字，用灰色小字、居中、字号比正文小一档。说明文字要写清来源，即使图片是自己截的也建议标注环境。

> 一条我坚持的判断标准：把文章打印出来读一遍。屏幕上被忽略的行高、间距和对齐问题，在纸上会立刻暴露出来。

## 一份可复制的检查清单

每次发布前，我会按这份清单过一遍：

- [x] 正文字号 ≥ 17px，行高 ≥ 1.7
- [x] 每行不超过约 45 个汉字
- [x] 中英混排处有可见间隙，标点前后无多余空格
- [x] 代码块可横向滚动且未被断行
- [x] 所有图片（若有）都有说明文字与来源
- [ ] 手机端实际滑动一遍，确认无溢出

最后一项永远保留为未勾选状态，因为**它必须每次都重新做**：排版规范能解决 90% 的问题，剩下的 10% 只有真机滑动才发现得了。
