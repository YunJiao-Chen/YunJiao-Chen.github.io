## 为什么又要折腾一次

我上一版博客是「成熟框架 + 一堆插件」的组合。它能跑，但每次坐下来写东西之前，我都要先想一遍：这篇要不要建目录、图片放哪、构建会不会因为某个依赖挂掉。写作的阻力从来不在于打字，而在于这些和写作无关的决策。真正让我下决心的是三件事：一次依赖升级让本地构建直接失败；文章列表在手机上要滚很久才能翻到旧文；以及我逐渐意识到，博客 99% 的访问量来自搜索引擎与社交分享，而不是登录、评论、个性化推荐这些必须依赖服务端的能力。

于是目标定得很朴素：内容是一堆 Markdown 文件，站点是这些文件的一次纯函数变换，产物是一堆静态 HTML。没有运行时依赖，我才敢相信五年后还能重建它。

## 主页的信息架构

我把主页从「最新文章瀑布流」改成了三段式，核心判断是：访客第一次来，需要知道「你是谁、写什么、从哪开始」，而不是看到第 20 篇旧文。

- **第一屏**：头像、签名、三行自我介绍、社交入口，以及一句当前状态（比如「正在写 Astro 实战系列」）。
- **第二屏**：五个固定分类卡片，每张给出定位描述与最近更新时间。
- **第三屏**：精选文章（`featured: true`）与最新 6 篇，配合标签做二次导航。

分类固定为五项，好处是它天然限制选题漂移：一篇文章如果塞不进任何一类，通常说明我还没想清楚自己要写什么。首页数据由 [Astro 内容集合](https://astro.build) 在构建期一次性取出，页面本身没有任何客户端请求。

## 构建流程：把所有决策写进脚本

新增文章不该是需要记忆的仪式。我用一个脚本生成带完整 frontmatter 的模板，用另一个脚本在构建后导出公众号 HTML：

```bash
# 新建文章：自动生成 slug 与 frontmatter
npm run new -- "中文排版规范"

# 本地预览（热更新）
npm run dev

# 构建站点并导出公众号 HTML
npm run build
```

配置被刻意拆成两处：`astro.config.mjs` 关心「怎么构建」，`site.config.ts` 关心「构建成什么样」。分类定义就是后者的一个数组，增删栏目不需要动任何组件代码：

```yaml
# site.config.ts 中的分类定义（示意）
- slug: frontend
  name: 前端工程
  icon: "◆"
  description: 框架原理、性能优化、构建工具与 CSS 工程化。
  accent: { from: "#6366f1", to: "#8b5cf6" }
```

## 部署：GitHub Pages 够用，而且免费

产物是静态文件，部署就退化成一次文件上传：推送到 `main`，Actions 里跑 `npm ci && npm run build`，再把 `dist` 上传成 Pages 工件。全流程约 90 秒，其中依赖安装占了一半。

> 静态站点最大的好处不是「快」，而是「不会坏」。没有进程会 OOM，没有连接池会被打满，也没有半夜的告警说首页 502。

代价是每次内容更新都要全量重建，构建时间随文章数增长。以我目前的规模（不到 100 篇），完整构建大约 10 秒，完全不值得引入增量构建的复杂度。这是典型的「现在不做，但心里清楚什么时候该做」的取舍。

## 我放弃了什么

放弃服务端渲染，就意味着放弃一些顺手的能力：站内搜索只能靠客户端索引，评论只能依赖第三方（我用 giscus），阅读量统计必须外挂服务。我接受这些取舍，因为它们都不是核心需求。但如果哪天我要做付费专栏或登录后的草稿同步，就得诚实承认：静态架构到头了，该加服务端了。

整个迁移花了两个周末，最耗时的不是写代码，而是把旧文章里 200 多个相对链接清洗干净。这件事枯燥，但它提醒我：内容才是需要长期维护的资产，框架只是它暂时的容器。
