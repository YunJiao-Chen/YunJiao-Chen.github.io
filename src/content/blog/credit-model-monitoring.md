## 上线当天就该建好的看板

模型上线后最怕的场景不是指标下跌，而是没人知道它跌了。我接手过一个已经跑了十一个月的评分卡，直到贷后同事抱怨某个渠道坏账异常，才有人回头去看 KS，发现它已经从 0.41 掉到了 0.29。这中间损失的不是模型精度，是响应时间。

所以我现在推动任何模型上线，第一件事是同时上线监控看板，而不是等出问题再补。监控要回答四个问题：区分度还在不在、分数分布有没有漂、策略端有没有被挤压、结果端是不是真的变差了。

## 区分度：KS 与 AUC 的正确读法

KS 和 AUC 都是排序能力的度量，但它们的敏感点不同。AUC 看全局排序，KS 看最优切点附近的区分，风控里更关心后者，因为决策通常落在几个固定分数阈值的邻域。

读这两个指标时要注意三件事：

| 现象 | 常见原因 | 处理动作 |
| --- | --- | --- |
| KS 与 AUC 同步缓降 | 客群结构缓慢变化 | 观察两到三个月，准备重训 |
| KS 骤降但 AUC 稳定 | 分数中段的排序被打乱 | 检查分箱边界与特征口径 |
| KS 稳定但坏账上升 | 策略阈值或额度政策变化 | 转策略侧排查，不动模型 |
| 全渠道同时异常 | 数据源或标签定义变更 | 立即停用模型，回滚版本 |

> KS 下跌本身不是结论，它只是一个信号。真正要回答的问题是：是模型过时了，还是模型之外的东西变了。

## 分数分布漂移：PSI 要分段算

PSI 是我最常用的漂移指标，但整条分数的单一 PSI 会掩盖局部问题。我的做法是把分数切成十档，分别算每档的占比变化，再汇总。这样能看出漂移是整体平移还是尾部翘起，两者的处置完全不同。

```sql
WITH base AS (
  SELECT width_bucket(score, 300, 900, 10) AS bin, COUNT(*) AS cnt
  FROM model_score
  WHERE score_date BETWEEN '2026-01-01' AND '2026-03-31'
  GROUP BY 1
),
curr AS (
  SELECT width_bucket(score, 300, 900, 10) AS bin, COUNT(*) AS cnt
  FROM model_score
  WHERE score_date BETWEEN '2026-07-01' AND '2026-09-10'
  GROUP BY 1
)
SELECT b.bin,
       b.cnt / SUM(b.cnt) OVER () AS base_pct,
       COALESCE(c.cnt, 0) / SUM(COALESCE(c.cnt, 0)) OVER () AS curr_pct,
       LN((b.cnt / SUM(b.cnt) OVER ()) / NULLIF(COALESCE(c.cnt, 0) / SUM(COALESCE(c.cnt, 0)) OVER (), 0)) AS psi_part
FROM base b LEFT JOIN curr c ON b.bin = c.bin
ORDER BY b.bin;
```

一般经验阈值是：PSI 低于 0.1 可接受，0.1 到 0.25 需要排查，超过 0.25 就该准备重训。但这个阈值要结合业务波动看，做促销的月份整条分布都会动，不能机械告警。

## 通过率与逾期率的联动

这是最容易被忽略的一环。模型只负责排序，通过率由策略决定。当通过率被人为抬高时，进入资产池的客群平均风险上升，逾期率跟着涨，但模型本身的区分度可能完全没变。反过来，如果通过率骤降，逾期率改善也可能只是分母变小。

我习惯把三条线画在一张图上：通过率、放款金额、FPD30。三条线的拐点如果同时出现，多半是策略调整；如果只有逾期线抬头，才轮到模型背锅。

## 预警阈值与迭代节奏

监控告警最忌讳只设一个总阈值。我一般分三层：

- 黄色：单月 KS 相对基线下降超过 10%，或分段 PSI 超过 0.1，记录并观察
- 橙色：连续两个月触发黄色，或 M3 逾期率相对预期偏离超过 20%，启动归因分析
- 红色：KS 相对基线下降超过 25%，或发现数据口径变更，直接回滚到上一版本

迭代节奏上我不追求频繁重训。没有明确归因结论的重训，只是把同样的错误换一个版本号。稳定客群下一年一次全量重建、每季度做一次校准回填，往往比每月重训更可靠。

真正的成本从来不是训练那几十分钟，而是每次上线带来的口径变更、策略联动和解释成本。
