## 先说结论

过去一年我用大模型做过四类信息抽取任务：合同要素抽取、财报指标抽取、工单分类、以及信贷材料里的字段补全。结论很明确：大模型擅长的是字段语义模糊、长尾形态多、样本稀缺的抽取；不适合的是字段固定、量极大、延迟敏感的场景。

判断标准其实可以用三个问题概括：字段定义有多模糊、每天要跑多少条、错了的代价有多大。下面展开。

## Schema 设计决定了一半的成败

我见过最多的失败案例不是模型不行，而是 schema 没设计好。两个原则：

第一，字段要么是原子值，要么是枚举，不要出现「自由文本段落」。让模型输出一段话，下游就没法用，也没法评估。第二，每个字段必须给出明确的缺失语义。是输出 `null`，还是输出空字符串，还是输出「未提及」？这三种在 prompt 里必须写死一种。

```python
from pydantic import BaseModel, Field

class ContractParty(BaseModel):
    name: str = Field(description='主体全称，未提及输出 未提及')
    id_no: str | None = Field(default=None, description='统一社会信用代码，18 位')
    role: str = Field(description='枚举：出借人 / 借款人 / 担保人')

class ContractExtract(BaseModel):
    contract_no: str
    parties: list[ContractParty]
    amount: float | None
    sign_date: str | None = Field(default=None, description='ISO 格式 yyyy-mm-dd')
```

用结构化输出约束（比如各家平台的 JSON schema 模式）比在 prompt 里反复叮嘱「只输出 JSON」可靠得多。加了约束之后，我们的解析失败率从 6% 降到 0.3%。

## Few-shot 还是微调

这是个成本问题，不是技术信仰问题。我目前的经验规则是这样的：

| 场景 | 推荐方案 | 理由 |
| --- | --- | --- |
| 字段少于 10 个，样本少于 50 条 | 纯 prompt 加 schema 约束 | 冷启动最快，改字段不动模型 |
| 字段稳定，样本 200 到 2,000 条 | few-shot，示例选边界样本 | 提升明显，无需训练基础设施 |
| 量极大且字段固定 | 蒸馏到小模型 | 单位成本能降一到两个数量级 |
| 字段频繁变更 | 不要微调 | 每次改字段都要重训，维护不起 |

我们那个合同抽取任务最终走的是第三条路：先用大模型标注出三万条高质量数据，再蒸馏到一个 300M 参数的小模型上。小模型的 F1 比教师模型低 0.03，但单条成本降了大约 40 倍，延迟从 1.8 秒降到 60 毫秒。

## 幻觉与校验：必须有一道程序化的闸门

大模型在抽取任务里最危险的失败模式是「编造一个看起来合理的值」。比如合同里没写金额，它给你填一个整数。这类错误人眼很难发现，因为格式完全正确。

我的应对是三层校验：

- 溯源校验：要求模型同时输出原文片段，程序验证该片段确实存在于输入里
- 格式校验：日期、金额、统一社会信用代码走正则和校验位规则
- 交叉校验：关键字段用两次独立抽取比对，不一致的进人工队列

> 抽取任务的评估指标不能只看准确率。我必看的一个指标是「幻觉率」，也就是输出值在原文中找不到依据的比例。这个指标超过 2% 就不能上线，无论准确率多高。

第三层交叉校验会显著增加成本，所以只对高风险字段启用，比如金额和主体名称。低风险字段单次抽取即可。

## 成本和延迟要算清楚

我评估一个抽取方案时会算四个数：单条 token 成本、P99 延迟、人工复核率、以及全量日成本。很多方案在 demo 阶段表现完美，一算全量就破产。

举个例子，某个场景每天 200 万条，单条平均 1,200 token 输入、150 token 输出，用中等规模模型的成本大约每天几千元。如果人工复核率是 5%，还要加上每天十万条的人工成本，这部分通常比模型调用贵得多。所以降低复核率往往比降低模型价格更划算。

## 什么时候不要上大模型

有三种情况我会直接拒绝：

1. 规则能覆盖 95% 以上的样本，且字段固定。这种情况下维护几十条正则比维护一个模型服务便宜得多，也更容易解释。
2. 延迟要求低于 100 毫秒。除非用蒸馏后的小模型或本地部署，否则网络往返就不够。
3. 没有评估集。没有评估集就没法知道模型是好是坏，上线等于赌博。

回到开头那句话：大模型是一个能力很强但很贵的工具。值不值得用，取决于任务模糊度、数据规模和错误代价三者构成的乘积，而不是取决于它有多新。
